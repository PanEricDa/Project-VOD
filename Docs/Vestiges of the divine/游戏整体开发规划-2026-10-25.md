# 《神代遗痕》整体开发规划：个人开发建议版

> 地图专项设计补充（2026-10-25）：地图部分以[地图与关卡设计-2026-10-25.md](地图与关卡设计-2026-10-25.md)为准。手工内容单元落实为固定地理中的软连接子区域，通过委托选取开放范围复用；不再以随机房间拼接作为地图基线。自由探索按主题地图指定委托逐步开放，终盘可加入整图全清计时挑战；本规划其他范围与里程碑不因此自动扩大。


日期：2026-10-25。
制作方式：个人开发，针对部分美术、音频及专项工作外包。
性质：基于现有文档与当前已完成战斗框架的宏观建议；供讨论收束，不是已冻结的首发内容表、日期承诺或自动执行授权。

## 一、当前阶段与下一目标

目前完成了已确认玩法范围内的战斗核心闭环：五人队伍、玩家聚怪与仇恨、伙伴自动战斗、专注、实时连携、评分、四伙伴终结技及评分效果奖励、基础胜负和重玩。

这证明了战斗可以运行和测试，尚不能据此换算整款游戏的完成百分比。接下来的产品目标是：玩家理解委托、完成战斗、获得收益，并愿意回到事务所为下一次行动作出选择。

推荐的游戏主循环：

事务所获得信息与委托
→ 选择任务、技能、装备和队伍方案
→ 进入遗迹，处理不同敌群与路线
→ 完成委托并结算
→ 回城，获得剧情反馈和可使用的收益
→ 投资事务所或调整构筑
→ 开始下一次行动。

近期最重要的可玩成果，是一个可以连续完成两次短委托、收益确实影响第二次准备的版本。

## 二、产品重心与范围控制

### 2.1 三个支柱

1. 战斗：玩家组织战场，AI承担基础职责，聚怪、连携与终结形成高潮。
2. 事务所：委托、人员、技能和装备选择，让战斗有前因后果，也承载经营与成长。
3. 世界与人物：后英雄时代的遗迹劳动者、潘奇城的日常和神代遗留问题，赋予重复行动以身份和意义。

建议以战斗与构筑为玩法重心，以轻经营连接行动，以人物与环境叙事形成辨识度。城市规模、建筑数量和剧情演出量都应服务这三个支柱。

现有 InitialStory.md 把基础经营视作叙事容器；若后续希望经营成为与战斗并重的玩法，需要重新核算整体范围，而不只是增加几个菜单。

### 2.2 保留与暂缓

保留目前五人队伍与四伙伴操作体系。旧评估报告中缩成两名伙伴的建议不覆盖当前已经验证的五人框架。开发阶段先用固定阵容，正式序章的招募顺序可随后按教学与叙事安排。

六个区域、四个先锋职业、更多伙伴、复杂经营、完整装备稀有度、隐藏终局等，作为远景内容池。它们的首发范围，在单章样板完成、生产成本可测量后冻结。

首个验证版本建议暂缓：自由布局建造、居民模拟、完整城市漫游、全随机地牢、大规模随机词缀、多职业批量生产、长篇动画过场、全面配音、无尽/赛季/长期更新体系。与单机完整发行的定位保持一致。

### 2.3 先明确的产品边界

- 面向玩家的主卖点与体验节奏：低精确操作负担的小队实时战术战斗。
- 一次委托的长度、整段章节的长度、重复刷取的必要程度。
- 经营承担多大失败压力，受伤、失败、撤退如何影响下一次行动。
- 角色强度主要来自技能选择、装备还是等级；先确定主导因素，避免几条成长线同步膨胀。
- 目标平台与操作方式：当前可按Windows PC和键鼠推进；手柄和其他平台按承诺范围加入验收。
- 目标美术风格、参考配置与性能目标。
- 明线的核心危机和终点。暗线不承担修补明线动力的职责。

这些内容优先写成简短范围表，而不是先扩写完整百科。

## 三、六个开发里程碑

| 阶段 | 目标 | 主要工作 | 通过条件 |
|---|---|---|---|
| 0. 收束范围 | 明确近期要做的游戏形状 | 游戏循环、主线骨架、成长主导线、表现风格、暂缓清单 | 能列出样板版本的明确内容，新增功能有取舍依据 |
| 1. 全流程灰盒 | 从战斗场景变成能重复行动的游戏 | 最小事务所/委托入口、手工关卡、少量敌人差异、一次构筑选择、奖励、存档、回城 | 无开发者指导完成一次出征，收益能影响下一次；退出重开保留应保留的数据 |
| 2. 单章质量样板 | 验证代表性品质与制作成本 | 一个区域、代表性敌人/精英/Boss、一段剧情、少量构筑、事务所可见升级、完整基本音画/UI | 陌生玩家能理解目标，战斗和回城都有动力；实测单位内容成本 |
| 3. 有限内容生产与主线贯通 | 按验证过的方式扩成可从头到尾通关的游戏 | 按章节扩展关卡、敌人、物品、人物事件与区域资产；完善必要外围系统 | 主线贯通、主要系统完整；以已测产能冻结首发数量 |
| 4. 整合与体验测试 | 把完整内容磨成稳定、可理解、节奏合理的体验 | 成长/经济/评分/专注联调、教学、可读性、性能、兼容性、存档迁移与长期流程测试 | 主要流程稳定，重要信息可读，多种合理方案能推进游戏，严重问题关闭 |
| 5. 发售准备 | 形成可交付产品 | 商店/试玩、版本管理、设置、操作与语言承诺、打包安装、宣传素材、发布检查 | 陌生机器可以安装运行、保存恢复和完成游戏；宣传与实际体验一致 |

测试从阶段1开始贯穿全程。阶段4负责集中整合，不是第一次让外部玩家接触游戏。

阶段1可以使用简化菜单和几何场景；阶段2必须有一段代表最终目标的真实品质，同时仍允许非关键内容简化。不要把样板变成需要完成全部系统才能开始的缩小版大工程。

## 四、各开发线如何安排

### 4.1 战斗关卡与敌人

这条线是下一阶段的主要投入之一。

先使用手工房间验证：开阔地、窄口、转角、远程敌人站位、可绕行路线，以及怪群之间的距离如何影响拉怪与聚怪。优先让同一套技能在不同地形里产生不同判断。

在现有近战与弓手基础上，先增加一类有明确施法表现的干扰敌人和一种精英。技能用现有SkillBase/Delivery/Effects实现；只有内容确实需要时才补控制等通用能力。

单章样板加入一个Boss，验证单目标与阶段变化下的专注、连携和终结节奏。必要的小怪与阶段安排可以保留聚怪特色，但不要求所有Boss复制杂兵战。

房间应成为可复用内容单元。程序化拼接只有在房间、连接和敌群节奏已经成立后才有价值。

正式地图需要纳入导航烘焙、移动边界、相机遮挡与大群怪物性能验收；已有测试中的导航基线问题应随地图规范处理。

### 4.2 技能、角色与编队构筑

先固定现有五人队伍，验证可替换技能与装备带来的差异，再增加更多职业与伙伴。

优先补的是“不同选择如何改变已有战斗”，例如聚怪效率、单体处理、范围连击、援护与风险取舍。首轮不需要每个角色都拥有大型技能树。

构筑入口先明确三件事：玩家选择什么、会牺牲什么、进入战斗后如何看见差异。技能槽已有，后续装配系统负责把选择接入现有槽位，不重新实现技能执行。

单机可以存在最优解；验收重点是多种合理方案可用、效果可理解，以及玩家愿意尝试。无需为了让所有组合等强而扩大制作范围。

角色外观、武器、动作端点与特写表现先确定一个实际可导入样品，再批量制作角色。避免先采购一批无法兼容现有动作与镜头需求的资产。

### 4.3 装备、遗物与成长

先选择一条主成长线，另外两条保持简单。例如先做少量明确特效的装备与技能选择，等级只提供温和数值增长。

首轮装备优先使用手工定义的确定效果。背包、装备比较、装卸、保存和实际效果都成立后，再考虑随机品质与词缀组合。

遗物作为改规则的少量高辨识内容后加入；消耗品则根据真实战斗需求决定，不为补齐物品分类而制作。

升级与装备会影响伤害、评分和专注收益，因此成长曲线必须与章节难度统一调试。不能分别提高攻击力、降低评分难度、提高专注回转后再把节奏失控归因于战斗框架。

### 4.4 事务所经营与建造

建议先做“功能设施选择＋可见升级”。

早期用委托桌、整备/训练、档案等少量功能点，让玩家把有限收益投入不同用途。升级应改变下一次出征的选择，而不仅是增加一个可点击按钮。

城镇服务和事务所自有建筑不必同时建设两套同功能系统。先划清哪些功能来自城里商人，哪些是事务所投入后的便利或能力。

建筑外观可以随升级逐步改善，提供从破办公室起家的成长反馈。自由摆放、网格建造、生产链、居民需求与NPC日程属于更高成本的独立玩法，需在轻经营已经有趣后再决定。

经营压力、重伤和破产结局先保留为设计议题。经济节奏可验证后再确定惩罚与恢复路径，避免首个原型被不可恢复的失败状态阻塞。

### 4.5 城镇与环境

先把潘奇城实现为一个小而有生活感的据点：事务所室内、一小段街道、少量关键NPC和服务入口。

通过招牌、回收遗物、客户、伙伴对白和升级前后变化表达社会志。世界观中写了一个街区，并不意味着首发必须制作成完整可步行地图。

城市主要承担归属感、准备和叙事。验证“回城之后想做什么”，再决定是否扩大漫游面积。

### 4.6 剧情与人物表现

现在就完成主线骨架，尽早选定事务所危机的具体形式及其游戏内后果。剧情事件与章节、委托、声望/经营变化建立对应关系。

叙事演出按成本分级：环境与道具描述、短对白/立绘或简单镜头、少量关键实时过场。高成本动画优先用于开场关键动作、危机与结尾等重要时刻。

先完成“接到第一张委托—队友反应—出征—回城交付”的小段演出，用它验证文本风格、信息节奏和工具链。

暗线早期保留每章线索位置与触发条件的规划，样板只验证一处隐藏发现。跨六区域的完整谜题和隐藏终局在明线与章节结构稳定后制作，不把假定的社区传播当成产品成立前提。

### 4.7 美术、动画、特效、音乐与声效

美术方向现在就要确定，资产批量生产随后展开。

先制作或外包一个可在Godot实际运行的样品包：一个角色/武器、一组区域模块、一套战斗信息色彩与UI样式，配合一次真实终结技特写。样品要同时通过普通战斗视角与特写镜头检查。

音效优先补：技能受理/失败、施放与命中、危险预告、治疗/保护、终结与结算。它们影响操作理解，应尽早进入样板。大量单位同时播放时，混音需要限制遮蔽与噪声。

早期音乐可用城镇与战斗两个代表性循环，后续按章节与关键战斗扩展。无需从第一阶段开始定制全量配乐或配音。

保留现有特效的独立源场景与Preview规范；视觉更新不能改变实际伤害和时间结算。

### 4.8 UI、存档与产品基础

UI随玩法一同制作：委托、整备、背包/装备、事务所投入、结算都先采用清楚可用的交互，再用统一视觉系统打磨。

存档应在第一次拥有永久收益时加入。需要明确角色/装备/技能装配、货币、解锁、任务与剧情标记的保存边界；一次出征状态与永久状态分开管理。回城结算不得重复领取。明确装备、技能解锁和资源中哪些永久保留、哪些仅在一次出征中生效；不默认引入失败清空或永久死亡规则。

为出征、结算、回城建立明确流程。现有战斗系统负责战场，外围系统提供装配与结果消费，避免城市、经营或UI直接改写伤害算法。

音量/显示/操作设置、暂停、可读性、字体与输入提示应在样板期间开始。手柄重绑定、语言与其他平台按最终产品承诺补齐。

## 五、首个样板的建议内容上限

以下是样板版本的讨论范围，不是首发承诺，也不是必须同时完成的开工清单。

| 内容 | 建议规模 |
|---|---|
| 队伍 | 现有1名玩家＋4名伙伴，先固定角色 |
| 据点 | 事务所室内＋少量服务入口；一段街道可在品质样板补入 |
| 委托 | 两次可连续体验的短委托，能复用区域资产但目标/战斗安排有差异 |
| 区域 | 一个主题区域，少量手工房间及路线变化 |
| 敌人 | 现有近战/弓手，逐步补一类特殊敌人、一种精英；品质样板再完成一个Boss |
| 构筑 | 一组能进行取舍的装备与技能选择，先验证两种可感知的准备方案 |
| 经营 | 一次有用途差异的投入选择，以及可见的事务所变化 |
| 剧情 | 一段任务引入、一次回城反馈、一处可选的隐藏发现 |
| 表现 | 覆盖本样板关键行为的基本音画与统一UI，不要求全量角色与场景最终精修 |
| 试玩 | 约20—30分钟完整体验，允许根据实际节奏调整 |

灰盒完成时先问“循环是否成立”；品质样板完成时再问“这种品质能否持续生产”。

## 六、适合外包什么

| 工作 | 建议 | 交付与验收重点 |
|---|---|---|
| 关键美术方向/概念 | 早期可少量外包 | 人物与场景风格能否统一，实际游戏镜头下是否适用 |
| 模块化环境、角色/武器模型 | 样品验证后分批外包 | 比例、材质、导入、命名、性能及源文件；交付Godot可用样例 |
| 图标与UI视觉 | 信息结构和技能含义稳定后外包 | 尺寸、风格、状态变体、可编辑文件及可读性 |
| 音效与混音 | 较适合优先外包 | 按游戏事件交付，在多单位实战中试听，不只听单独文件 |
| 音乐 | 风格和场景节奏稳定后外包 | 可循环、可分层/过渡、统一响度及使用授权 |
| 特定动画/VFX | 选择困难且收益高的部分 | 符合现有动作端点/方法事件、材质及Preview规范，实机可验收 |
| 宣传图/预告片/专项测试或翻译 | 有稳定样板后按需外包 | 与实际产品一致，有明确素材、文本和测试范围 |

建议自行掌握：玩法取舍、整体数值、AI职责、关卡遭遇、构筑关系、经营反馈、存档与集成，以及最终验收。核心剧情方向也应由自己决定，文字编辑或翻译可后续协作。

外包从一个小样品开始。验收通过后才批量委托；每包写清资产规格、源文件、可商用使用范围和Godot接入要求，保留自己集成与返修的时间。

## 七、个人开发的工作节奏

同时推进一条主实现线和少量可独立验收的外包工作。并行不意味着每天在剧情、装备、城市和Boss之间切换。

每个可玩版本只解决一个主要未知问题；用完成后的游戏体验验收，而不只统计新脚本和系统数量。

保留三个内容列表：当前里程碑必须完成、首发候选、未来设想。新想法进入候选，不自动进入当前任务。

记录一间房、一个敌人、一项技能、一个剧情事件从制作到接入/测试的实际成本，再估算后续内容量。留出迭代、外包沟通、整合与修复空间，避免以满负荷制作速度承诺整款游戏工期。

阶段3应完成主线从开场到结局的粗贯通，防止开场高度精修而后半段长期空缺。之后再做统一品质提升。

## 八、测试与发行

阶段1用少量陌生玩家观察：是否能自己找到委托、理解准备、完成战斗、领取收益并做下一次选择；失败后是否知道原因；不同准备是否产生可感知变化。

阶段2同时测试体验与生产效率，并开始整理可公开展示的稳定片段。若计划上Steam，此时可以考虑商店素材与后续试玩安排，而不是等到全部内容做完才接触玩家。

Steam Playtest使用关联但独立的测试AppID，适合后续招募和分批测试。具体发布与账户操作另行安排，不由本规划自动执行。

阶段3以后持续验证完整存档、长时间连续委托、失败恢复、剧情条件、奖励幂等、大群怪物性能与目标设备表现。每个里程碑形成可运行版本与清楚的版本记录。
